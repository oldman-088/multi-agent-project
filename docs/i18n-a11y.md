# Internationalisation coverage and accessibility suite

This document covers the two quality gates added for AATM-732b98ff
(SPEC §8.2, §9):

1. **i18n coverage** — `apps/web/src/i18n/` with `ar`, `en` and `fa`
   catalogues plus a check that **fails** when a translation key is missing.
2. **Accessibility** — `tests/a11y/` with axe checks for every main page, and
   RTL/LTR screenshots of the frontend in Arabic and English (plus Persian).

It also documents how `<html dir>` and `<html lang>` are derived from the active
language, which is the third acceptance criterion.

---

## 1. Translation catalogues — `apps/web/src/i18n/`

| File | Purpose |
| --- | --- |
| `languages.ts` | The shipped set (`ar`, `en`, `fa`), their direction, native names, the `localStorage` key and `resolveInitialLanguage()`. |
| `locales/en.ts` | **Reference** catalogue — defines the key set. |
| `locales/ar.ts` | Arabic (default language, RTL). |
| `locales/fa.ts` | Persian (RTL; exercises پ چ ژ گ and Persian digits). |
| `resources.ts` | Aggregates the catalogues; the only module that imports all three. |
| `coverage.ts` | Pure rules: missing key, empty value, non-string value, extra key, `{{placeholder}}` mismatch. |
| `direction.ts` | `documentLanguageAttributes()` and `applyDocumentLanguage()` — the `<html lang/dir>` writer. |
| `i18next.ts` | The single i18next instance, `missingKeyHandler`, persistence. |
| `I18nProvider.tsx` | react-i18next provider + lifetime `lang`/`dir` sync + `useActiveLanguage()`. |
| `format.ts` | Locale-aware number, date, currency and relative-time formatting. |

Catalogues are **flat, dot-delimited keys** (`connection.browser.step1`), not
nested objects, so a coverage diff is a single readable list and
`keySeparator: false` is explicit in the i18next init.

### The failing check

```bash
npm run i18n:check          # exit 1 on any missing/empty/extra/mismatched key
npm run i18n:check -- --json            # machine-readable report
npm run i18n:check -- --allow fa        # report a draft locale without failing
```

It is implemented twice, from the **same rules** in `coverage.ts`:

- `apps/web/scripts/check-i18n.mjs` — the CLI that CI runs. It imports the `.ts`
  modules directly via type stripping, which is unflagged from **Node 22.18**;
  `engines.node` is therefore `>=22.18.0` in both `package.json` files, and CI
  uses Node 22. (Older Node needs `--experimental-strip-types`, which the script
  does not rely on.)
- `apps/web/src/i18n/coverage.test.ts` — 22 unit tests including negatives for
  every rule.

Verified failure mode (a key removed from `fa.ts`):

```
check-i18n: FAILED — 2 problem(s) across 1 locale(s).
  [placeholder-mismatch] placeholders for "error.timeout" in fa: missing {{seconds}}
  [missing-key] missing "nav.dashboard" in fa
```

At runtime the same guarantee is enforced by i18next's `missingKeyHandler`
(`saveMissing: true`, `saveMissingTo: 'all'`), whose behaviour follows the build:

| Build | `throwOnMissingKey` | Result |
| --- | --- | --- |
| development / Vitest (`import.meta.env.DEV`) | `true` | throws — a gap cannot be missed |
| production bundle | `false` | logs `console.error` and renders the key name |

The message names every locale the lookup searched **and** the active one, e.g.

```
[i18n] missing translation key "nav.dashboard" (namespace "translation") for fa, ar — active language "fa"
```

(`saveMissingTo: 'all'` is required here: i18next's default `'fallback'` reports
only the fallback locale, which made the message always say `ar`.)

In production a missing key degrades; it never blanks the product.
`TranslationErrorBoundary` (`src/i18n/TranslationErrorBoundary.tsx`) wraps each
page **inside** the shell (`App.tsx`), not the whole app: a render failure in
translated content is replaced by a readable panel in the active language with a
working `h1` and a real retry, while the header, navigation and skip link keep
working. `tests/a11y/boundary.a11y.spec.ts` proves this in a real browser in both
Arabic (RTL) and English (LTR), including axe on the degraded state.

### Scope note

`apps/web/src/i18n/` and `tests/a11y/` are the task deliverable. The surrounding
shell (`src/pages/`, `src/components/`, `src/styles/`, `src/App.tsx`,
`src/routes.ts`, `src/main.tsx`) exists because `main` ships no frontend at all;
without a page to render, the coverage, direction and axe criteria cannot be
tested. It is deliberately small, logical-properties-only, and free of business
logic — no API calls, no state machines, no data layer. If the project wants it
owned by the frontend worker instead, it can be split out cleanly: the a11y
suite depends only on the dev server and on `src/routes.ts`.

## 2. `<html dir>` and `<html lang>` from the active language

SPEC §8.2: *"Set `<html dir>` and `lang` from the active language."* There is no
hand-written `dir` or `lang` in `apps/web/index.html` — the attributes are always
derived:

| Language | `lang` | `dir` |
| --- | --- | --- |
| `ar` (default) | `ar` | `rtl` |
| `fa` | `fa` | `rtl` |
| `en` | `en` | `ltr` |

Two layers apply it:

1. **Pre-paint** — a small inline bootstrap in `index.html` reads
   `localStorage["nexus.language"]`, then `navigator.languages`, then defaults to
   Arabic, so the first paint is already in the right direction (no flash).
2. **Runtime** — `I18nProvider` calls `syncDocumentLanguage()` and i18next's
   `languageChanged` handler calls `applyDocumentLanguage()`, so the switch is
   applied the moment the owner changes the language, and the choice is
   persisted.

Covered by `apps/web/src/i18n/direction.test.ts` (16 tests) and by the
Playwright assertion `expectDocumentLanguage()` in every a11y and screenshot
test. Layout mirroring is asserted separately (`expectMirroredLayout()`): the
brand sits on the inline-start edge and the header controls on the inline-end
edge, which is the right edge in RTL — a stylesheet that sets `dir` but keeps
physical `left`/`right` positioning fails the build.

All stylesheets use logical properties only (`margin-inline`, `padding-inline`,
`inset-inline-start`, `border-inline-end`, `text-align: start`); there is no
`margin-left`, `left:`, `right:` or `text-align: left/right` in
`apps/web/src/styles/`.

## 3. Accessibility suite — `tests/a11y/`

```bash
npm run test:a11y      # everything: axe + screenshots, against the Vite dev server
npm run screenshots    # only the @screenshots project
npm run a11y:dist      # same suite against a production build (vite preview :4173)
```

| File | Contents |
| --- | --- |
| `playwright.a11y.config.ts` | Two projects — `a11y` and `screenshots`; starts the Vite dev server on `0.0.0.0`. |
| `pages.a11y.spec.ts` | axe on 5 pages × 3 languages, plus four interaction states. |
| `main-pages.screenshots.spec.ts` | RTL/LTR screenshots of the main pages. |
| `harness.a11y.spec.ts` | Negative controls proving the axe harness can fail. |
| `support/axe.ts` | `expectNoAxeViolations()` with explicit WCAG 2.0/2.1/2.2 A+AA and best-practice tags. |
| `support/locales.ts` | Locale/page matrices, `openAs()`, `expectDocumentLanguage()`, `expectMirroredLayout()`. |
| `tsconfig.json` | Typechecks this folder; included in `npm run typecheck` and therefore in CI. |

`MAIN_PAGES` is **derived** from the app's own route table
(`apps/web/src/routes.ts`), not hand-written, so a new page automatically joins
the axe and screenshot matrices. `apps/web/src/routes.test.ts` is the guard: it
fails if a route is not reachable from the primary navigation, if a title or nav
label is missing from any of the three catalogues, or if `App.tsx` and
`routes.ts` disagree about which pages exist.

### Coverage

- **axe**: 5 main pages (dashboard, Connection Manager, agents, runs, settings) ×
  3 languages = 15 runs, plus the Connection Manager after three wizard steps,
  the light theme, and the skip-link/keyboard path — 19 checks in total.
- **Negative controls** (5 tests) prove the harness is not vacuous: an image
  without `alt`, low-contrast text, an unnamed button and a missing
  `<html lang>` must all be reported; a clean fragment must pass.
- **Screenshots**: Arabic (RTL) and English (LTR) for all five main pages, plus
  Persian (RTL) for the Connection Manager — 11 images, written to
  `docs/screenshots/a11y/<lang>-<dir>/<page>.png`.

Each screenshot is taken only after the document language, the page heading and
the mirrored layout have been asserted, so an image cannot silently capture a
broken page.

### Running without access to Playwright's CDN

CI installs Chromium with `npx playwright install --with-deps chromium`. In an
air-gapped sandbox, point the suite at any compatible Chromium binary:

```bash
NEXUS_CHROMIUM_EXECUTABLE=/path/to/chromium \
LD_LIBRARY_PATH=/path/to/nss-libs \
npm run test:a11y
```

`PLAYWRIGHT_BASE_URL` skips the managed dev server and runs the suite against an
already-running instance. `npm run a11y:dist` builds `apps/web`, starts
`vite preview` on port 4173 itself (via `NEXUS_PREVIEW=1`), and points the specs
at it — pass `PLAYWRIGHT_BASE_URL` to override the target.

## 4. Reproducing the gates

```bash
npm ci
npm run typecheck     # tsc --noEmit for src, for the vite/vitest configs, and for tests/a11y
npm run i18n:check    # fails on a missing key
npm run test:unit     # 70 jsdom tests: coverage rules, dir/lang, formatting, page render
npm run build         # production bundle
npm run test:a11y     # 35 Playwright tests: axe + screenshots
```

GitHub Actions runs the same set in `.github/workflows/web.yml`
(`i18n-and-unit` and `a11y` jobs), uploading the screenshots as an artifact.
